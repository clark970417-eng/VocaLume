# 4.4.8 request reuse verification — 2026-10-25

## Implemented scope

The desktop translator shares an identical in-flight translation and reuses completed outputs in memory (128 entries, five-minute expiry). The complete input, language pair, model options, writing register and glossary are part of the key. Context is snapshotted before queueing so later glossary edits cannot change a pending request under its original cache key. HY-MT still omits previous utterances, exactly as its existing worker prompt did.

Each waiting caller has independent cancellation. Shared inference is cancelled only after all callers leave. Empty, failed, cancelled and superseded work is not retained. Disposal clears results and cancels waiting callers. Incremental/SimulMT/SSBD requests keep their existing paths. The normal worker queue, model, prompts, sentence boundaries and caption presentation order are unchanged.

The extension now shares identical native requests across its local translation paths before crossing the native bridge. It retains the existing 200-result in-memory memo capacity; failed calls can be retried. Different language directions, writing styles or fast/quality choices use separate keys. This does not enable website translation: explicit opt-in from 4.4.7 remains required.

## Measurements

Machine: Apple M5, 16 GB. Existing local HY-MT1.5-1.8B Q4_K_M, standard Metal backend, 33 GPU layers. The benchmark uses an isolated profile and existing model files, with no browser messages, audio capture or network translation. Baseline source: `b2edd3a`. The final measured run executes optimized then baseline after an initial development comparison. Other desktop applications remained running; this is not an isolated hardware benchmark.

Twelve authored Japanese/Traditional Chinese sentences produce 20 comparison records, including intentional repeated and concurrent requests. All 20 output records match the baseline exactly. The test deliberately includes duplicate inputs to exercise reuse; the inference count is not a prediction of a typical livestream's workload.

| Operation | Samples | Baseline median | 4.4.8 median |
| --- | ---: | ---: | ---: |
| First translation of a sentence | 8 | 980 ms | 883 ms |
| Repeat of a completed sentence | 8 | 799 ms | 1.58 ms |
| Two concurrent identical requests, both complete | 4 pairs | 1592 ms | 903 ms |

The native inference count for this authored workload falls from 24 to 12. The cache accounts for the repeat/concurrent improvement. The first-time timings vary with other activity and do **not** establish faster generation for new sentences. Startup/model loading, speech recognition, sentence completion waits and subtitle display are excluded. Reduced inference count is not a temperature, energy or long-duration stability measurement.

Raw authored cases, complete outputs and timing records: [request-reuse results](4.4.8-request-reuse.json). Existing model wording errors may remain; matching the baseline is a regression check, not proof of translation accuracy.

## Reproducing the text probe

`scripts/benchmark-request-reuse.ts` runs the authored cases through the actual Electron translator and UtilityProcess worker. Build the production app, then bundle the script with esbuild using `--bundle --platform=node --format=cjs --packages=external --outfile=out/main/benchmark-request-reuse.cjs`. Run it with Electron and set `COMPARE_PROFILE` to an isolated test directory containing the existing model files, `COMPARE_REPORT` to a JSONL output path, and `COMPARE_LABEL` to identify the version. Run the same script against the baseline translator source for comparison. Keep measurement sequential and avoid builds/tests during inference.
